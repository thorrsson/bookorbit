# Azure deployment

The default target is one Ubuntu 26.04 LTS VM running the existing app and PostgreSQL Compose stack, with Caddy for automatic HTTPS at **https://library.the3littlesisters.com**. A separate, opt-in target provisions Container Apps, managed PostgreSQL and Azure Files. Both targets use the same published application image, public hostname and container paths. No Azure resource is created or DNS record changed by CI or by installing the tooling.

The tooling deploys the **core stack**. The optional read-aloud/TTS workers, download clients, private container registries, custom CA mounts and feature-specific environment overrides need additional deployment configuration. Unsupported runtime settings fail validation instead of being silently dropped.

## Prerequisites

- An Azure subscription and permission to deploy into an existing resource group.
- Azure CLI, Bicep CLI, Ruby 3.2+ with Minitest, `jq`, SSH and Docker Compose 2.24.4+. Docker Buildx is useful for inspecting image digests.
- A DNS hostname you control. The VM needs inbound TCP 80/443 for HTTPS and SSH restricted to your administrator IP range.
- Published **Linux amd64** app, PostgreSQL and Caddy images, pinned by SHA-256 digest. The existing Container Image workflow already publishes the application to GHCR; a second build pipeline or ACR is not needed.

Initialize your local Node environment as usual if using the optional `pnpm azure` and `pnpm test:azure` aliases. The Bash entry points below do not need Node or workspace dependencies.

## Single VM

### 1. Select the subscription and configure infrastructure

```bash
az login
export AZURE_SUBSCRIPTION_ID=YOUR_SUBSCRIPTION_ID
az account show --subscription "$AZURE_SUBSCRIPTION_ID" --query '{name:name,id:id}' -o table
az group create --subscription "$AZURE_SUBSCRIPTION_ID" --name bookorbit-vm-prod --location westus3
cp infra/azure/vm.parameters.example.json infra/azure/vm.parameters.local.json
```

Edit the local parameters file with the **contents** of your SSH public key and your real administrator IPv4 CIDR, normally `/32`. The wrapper rejects CIDRs broader than `/24`. Choose a region with the VM size available. The default is 2 vCPUs, 8 GiB RAM and a 128 GiB Premium SSD data disk; size the disk for your books, covers, database, temporary work and backup headroom.

```bash
bash scripts/azure/azure.sh plan vm bookorbit-vm-prod infra/azure/vm.parameters.local.json
bash scripts/azure/azure.sh apply vm bookorbit-vm-prod infra/azure/vm.parameters.local.json
```

Use the returned `sshTarget` and `ipAddress`. In the `the3littlesisters.com` DNS zone, point the `library` A record to that IP when you are ready to move traffic. Remove or correct any conflicting CNAME or stale AAAA record.

The template creates a static public IP, restricted NSG, passwordless SSH VM and separate data disk. Cloud-init formats only a blank LUN 0 disk, mounts it at `/srv/bookorbit`, and installs Docker Engine and the Compose plugin from Docker's official apt repository, plus transfer tools. It refuses to overwrite a recognized non-ext4 filesystem. Docker requires the data mount, preventing a missing disk from silently redirecting writes to the OS disk.

First connect using normal SSH and verify the host fingerprint against Azure's console before accepting it into `known_hosts`. The deployment command requires an already trusted host key and uses your SSH agent/default key. Add a non-default key to your agent rather than disabling host verification.

Cloud-init runs only when creating the VM. Changing its source and reapplying Bicep does not patch an existing guest. The default `Standard_D2as_v6` size uses an NVMe disk controller. Disk discovery uses the `azure-vm-utils` LUN links, so SCSI sizes also work if you set `diskControllerType` to `SCSI` when choosing one.

### 2. Generate and protect runtime settings

```bash
bash scripts/azure/azure.sh init-env .env.azure.local
docker buildx imagetools inspect ghcr.io/thorrsson/bookorbit:main
docker buildx imagetools inspect pgvector/pgvector:pg18
docker buildx imagetools inspect caddy:2-alpine
```

Edit `.env.azure.local`:

- Confirm `APP_URL=https://library.the3littlesisters.com`, which is generated by default.
- Replace each `REPLACE` with the corresponding image's top-level `Digest`. Keep `POSTGRES_IMAGE=pgvector/pgvector:pg18@sha256:...`; changing database major versions requires a separate PostgreSQL upgrade.
- Leave the generated secrets unchanged on future deployments. If importing an existing installation, preserve its signing/encryption keys and database credentials instead of generating replacements.

`init-env` writes mode `0600` and refuses to overwrite an existing file. Runtime files are a deliberately simple `KEY=value` format: no shell commands, interpolation, quotes, whitespace or trailing comments. They are parsed as data, never sourced as shell code. Generated secrets are random hexadecimal strings.

Do not pass secrets as CLI arguments, put them in infrastructure parameters, enable shell tracing, or commit runtime files. `*.local` and `infra/azure/*.local.*` are ignored. Secure ARM parameters are injected through a private temporary file, removed on exit; secrets are never included in cloud-init or deployment outputs.

### 3. Deploy

```bash
bash scripts/azure/azure.sh deploy-vm azureuser@YOUR_VM_IP .env.azure.local
```

The command waits for cloud-init, transfers this checkout's Compose files and configuration over SSH, validates and pulls pinned images, then waits for application health and checks the public HTTPS health endpoint. DNS must already point to the VM for Caddy to obtain its certificate. No new application build happens on the VM.

Complete the setup wizard using `SETUP_BOOTSTRAP_TOKEN` from your protected settings file. Do not remove the token from the environment afterwards: production startup requires it.

Persistent state is independent of release directories:

| Host path                           | Container path            | Contents                                      |
| ----------------------------------- | ------------------------- | --------------------------------------------- |
| `/srv/bookorbit/state/books`        | `/books`                  | Libraries and `/books/.book-dock`             |
| `/srv/bookorbit/state/app`          | `/data`                   | Covers, avatars, app-managed files and caches |
| `/srv/bookorbit/state/postgres`     | PostgreSQL data directory | Database                                      |
| `/srv/bookorbit/state/caddy-data`   | Caddy `/data`             | TLS certificates                              |
| `/srv/bookorbit/state/caddy-config` | Caddy `/config`           | Proxy state                                   |

Copy/import your book files into the `books` directory, preserving writable ownership for the configured `PUID`/`PGID`. Create libraries under `/books` in the UI. Do not configure library paths pointing into release directories.

Only Caddy publishes ports 80/443. Neither the app nor PostgreSQL has a host-published port. `/books` and Book Dock share a filesystem so local hardlinks can work.

### TLS certificates

The VM uses [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https): public certificates are obtained and renewed automatically using ACME providers such as Let's Encrypt, and HTTP redirects to HTTPS. Certificate state persists on the data disk. There is no separate Certbot job, paid certificate or Azure gateway to operate. Keep your domain's A/AAAA records correct and ports 80/443 reachable for validation and renewal.

Container Apps instead uses **Azure's free managed certificates**, also automatically renewed. The default Azure hostname is already HTTPS; your own hostname needs DNS ownership validation and a managed-certificate binding. The migration steps below include that command. No certificate private key is copied from the VM to Azure.

### Updates, backups and recovery

Change only the desired image digest in the existing runtime file, then run `deploy-vm` again. Updates take a short maintenance window: images are pulled first, the app is stopped, and a PostgreSQL custom-format dump is taken **before** the new app can apply migrations. Failed backups block the upgrade. Changed database credentials or application signing/encryption keys also block upgrades.

The app's existing entrypoint performs migrations. A failed startup stops the new app and reports the failed release directory; it does not automatically start an old image against a possibly migrated database. The `current` symlink changes only after Compose health succeeds. A later public HTTPS failure is reported but does not undo a successful database migration.

Export a consistent database and media snapshot:

```bash
bash scripts/azure/azure.sh export-vm azureuser@YOUR_VM_IP /secure/backups/bookorbit-2026-11-25.tar
```

The source app is stopped for the entire export, then resumed only if it was previously running. The archive streams over SSH without loading the library into memory or duplicating media on the VM. The VM needs space for a database dump; the destination needs space for the full archive. Pause **external** library writers separately. Exports and deployments are mutually exclusive.

Archives contain the database dump, books, app data, proxy state, deployed Compose files and credentials. They do **not** copy a live PostgreSQL data directory. They are mode `0600`; store them encrypted, off the VM, with access controls and retention. A failed transfer leaves an unverified `.partial` file for inspection, not a successful backup. Protect or securely remove it as well. Pre-deploy dumps remain on the data disk and are not disaster-recovery backups. Monitor free space and remove superseded releases/dumps only after confirming your retention and restore requirements.

Before production use, perform a restore drill into an isolated replacement VM: restore the protected configuration and media, start the matching PostgreSQL 18 image, restore `database.dump` with a PostgreSQL 18 `pg_restore`, and start the **same pinned app image**. Check login, book counts, reading progress, downloads, uploads and Kobo/KOReader sync. Retain the original until the restored instance is verified.

For a failed schema upgrade, keep the app stopped. Select the recorded `previous-release` from the pre-deploy backup, restore that backup into a clean database, then start the matching previous image/configuration and verify health. If the failed release modified library/app files, restore matching media too; the automatic pre-deploy dump covers only PostgreSQL. This is a deliberate restore, not an automatic image rollback; restoring a backup discards writes after that backup.

The data disk detaches when the VM is deleted, but deleting the **resource group** deletes the disk too. Never treat disk retention as a backup. You still own OS/container updates, backup scheduling, monitoring and restore testing. Configure availability alerts, disk-space alerts and off-VM backup retention before relying on the service.

## Opt-in Container Apps migration

This is a **separate deployment**, preferably in a separate resource group, not a switch that deletes/replaces the VM. Nothing in this section is provisioned for VM deployments.

The platform template provisions:

- A workload-profiles Container Apps environment and Log Analytics.
- Private-network PostgreSQL 18 with 14-day backups and the required `uuid-ossp`, `pg_trgm`, `unaccent` and `vector` extensions allowlisted.
- Two Premium Azure Files **NFS** shares, preserving `/books` and `/data`, restricted to the app subnet and optionally the source VM subnet.
- Private PostgreSQL DNS and optional source-VNet DNS linking and one-way peering for migration.

NFS is intentional: POSIX ownership and hardlinks are closer to the VM filesystem than SMB. Container Apps currently cannot encrypt NFS mounts in transit, so the template disables storage's HTTPS-only requirement and restricts access using virtual-network service endpoints and a default-deny firewall. Data is encrypted at rest. NFS permits root on the allowed network so the existing entrypoint can repair ownership. If your policy requires encrypted NFS transport or root squashing, do not deploy this target unchanged. See [Microsoft's storage guidance](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts).

Premium file-share capacity, managed PostgreSQL, logs and an always-on app incur charges even without requests. Size both shares before copying your library; each defaults to 100 GiB. Keep a separate file-share backup policy, since PostgreSQL backups do not cover books or app data.

### 1. Provision dependencies without starting the app

Register `Microsoft.App`, `Microsoft.DBforPostgreSQL`, `Microsoft.Storage`, `Microsoft.Network` and `Microsoft.OperationalInsights` if these providers are not registered in your subscription. Install the Azure CLI Container Apps extension when needed:

```bash
az extension add --name containerapp --upgrade
az group create --subscription "$AZURE_SUBSCRIPTION_ID" --name bookorbit-apps-prod --location westus3
cp infra/azure/container-apps-platform.parameters.example.json infra/azure/container-apps-platform.parameters.local.json
```

Set `migrationVirtualNetworkId` and `migrationSubnetId` to the VM template's outputs. The VM subnet already has a Storage service endpoint. Networks must have non-overlapping address spaces; defaults are `10.40.0.0/24` for the VM and `10.42.0.0/16` for Container Apps.

```bash
bash scripts/azure/azure.sh plan container-apps-platform bookorbit-apps-prod infra/azure/container-apps-platform.parameters.local.json .env.azure.local
bash scripts/azure/azure.sh apply container-apps-platform bookorbit-apps-prod infra/azure/container-apps-platform.parameters.local.json .env.azure.local
```

Save the returned `postgresHost`, `storageAccountName` and `virtualNetworkId`. The source runtime file supplies the PostgreSQL username/database/password; no app is deployed yet. The [extensions allowlist](https://learn.microsoft.com/en-us/azure/postgresql/extensions/how-to-use-pgvector) permits installation during restore/startup, but does not itself execute SQL.

Complete the reverse peering from the source VNet:

```bash
az network vnet peering create --subscription "$AZURE_SUBSCRIPTION_ID" \
  --resource-group bookorbit-vm-prod --vnet-name bookorbit-vnet \
  --name container-apps --remote-vnet YOUR_APPS_VNET_RESOURCE_ID --allow-vnet-access
```

Adapt names if you changed `name`. Verify both peerings are `Connected` and the source VM resolves/reaches the private PostgreSQL hostname before proceeding.

### 2. Rehearse transfer and restore

On the source VM, mount the dedicated, initially empty destination shares. Substitute the non-secret storage account name:

```bash
STORAGE_ACCOUNT=YOUR_STORAGE_ACCOUNT
sudo mkdir -p /mnt/bookorbit-books /mnt/bookorbit-data
sudo mount -t nfs -o vers=4.1,sec=sys \
  "$STORAGE_ACCOUNT.file.core.windows.net:/$STORAGE_ACCOUNT/books" /mnt/bookorbit-books
sudo mount -t nfs -o vers=4.1,sec=sys \
  "$STORAGE_ACCOUNT.file.core.windows.net:/$STORAGE_ACCOUNT/data" /mnt/bookorbit-data
mountpoint /mnt/bookorbit-books
mountpoint /mnt/bookorbit-data
```

Rehearse file transfer using `rsync -a --numeric-ids --partial --info=progress2` from `/srv/bookorbit/state/books/` and `/srv/bookorbit/state/app/` to their corresponding mounts. This supports resumable, incremental transfers and preserves numeric ownership. Hardlinked source files become independent destination files with this command; budget for the additional space. Preserve original container paths so database file references stay valid.

Test a PostgreSQL 18 custom-format dump/restore into the new database using `pg_restore --no-owner --no-acl --exit-on-error`. Use `sslmode=verify-full` and an owner-only `.pgpass` file, not a password in shell history or process arguments. Run the restore from the peered VM, not the public internet. Do not start a second app against the destination during bulk transfer.

For a production migration, rehearse against a disposable database/share copy first. Do not overlay a final restore onto a populated rehearsal database: recreate the empty target database deliberately before the final restore.

### 3. Quiesce, final-sync and restore

Arrange a maintenance window, pause external writers, then stop the source app. On the source VM:

```bash
set -euo pipefail
release="$(sudo readlink -f /srv/bookorbit/current)"
compose=(sudo docker compose --project-name bookorbit --env-file "$release/.env"
  -f "$release/docker-compose.yml" -f "$release/compose.vm.yml")
"${compose[@]}" stop --timeout 60 app
```

Repeat the file transfer while the app is stopped. If you pre-seeded, inspect `rsync --dry-run --delete` first and only synchronize deletions after confirming both destination mountpoints and that the shares belong exclusively to this migration. Otherwise files deleted since the pre-seed can reappear when scanned. Keep the source files untouched.

With a PostgreSQL **18** restore client installed on the peered VM and the target password in `~/.pgpass`:

```bash
export PGHOST=YOUR_MANAGED_POSTGRES_HOST
export PGUSER=bookorbit PGDATABASE=bookorbit PGSSLMODE=verify-full
"${compose[@]}" exec -T postgres sh -c \
  'exec pg_dump --username="$POSTGRES_USER" --dbname="$POSTGRES_DB" --format=custom' \
  | pg_restore --no-owner --no-acl --exit-on-error
```

Use your configured username/database if different. Keep `pipefail` enabled so a failed source dump cannot be reported as a successful restore.

### 4. Start the managed app, verify, then cut over DNS

Copy the **existing** protected runtime file to `.env.azure-apps.local`, preserving all signing/encryption keys, credentials and `PUID`/`PGID`. Add `DATABASE_URL` with the managed PostgreSQL hostname and `?sslmode=verify-full`; URL-encode credentials if necessary. Keep `APP_IMAGE` at the exact digest running on the source for this first cutover, and keep `APP_URL` at your intended public hostname.

```bash
cp infra/azure/container-app.parameters.example.json infra/azure/container-app.parameters.local.json
bash scripts/azure/azure.sh plan container-app bookorbit-apps-prod infra/azure/container-app.parameters.local.json .env.azure-apps.local
bash scripts/azure/azure.sh apply container-app bookorbit-apps-prod infra/azure/container-app.parameters.local.json .env.azure-apps.local --confirm-cutover
```

The flag is your acknowledgement that source writers are stopped; the tooling cannot inspect external writers. The image applies migrations before serving. Health probes allow up to 30 minutes for startup, while liveness uses TCP so a temporary database outage does not force application restart loops.

Check the returned Azure HTTPS URL at `/api/v1/health`, then test login, file ownership, scans, uploads, downloads, audiobook range requests, WebSockets and Kobo/KOReader. Network filesystems do not guarantee local filesystem-watch events for remote writes: configure scheduled scans and verify ingestion behavior, not just HTTP health.

Use [Container Apps custom-domain setup](https://learn.microsoft.com/en-us/azure/container-apps/custom-domains-managed-certificates) to obtain the generated hostname and domain verification code. At cutover, replace the `library` A record with a CNAME **directly** to the app's generated hostname and add the `asuid.library` TXT verification record in the `the3littlesisters.com` zone. An intermediate proxy/CNAME chain, including Cloudflare's proxied mode, prevents managed-certificate issuance/renewal. If you have restrictive CAA records, permit `digicert.com` for Azure as well as your VM's ACME issuer.

Once DNS is ready, create/bind the free managed certificate and verify trusted HTTPS:

```bash
bash scripts/azure/azure.sh bind-domain bookorbit-apps-prod bookorbit .env.azure-apps.local CNAME
```

For an apex domain, use the environment's static IP in an A record, the apex `asuid` TXT record, and pass `HTTP` instead of `CNAME`. The command derives the hostname from `APP_URL`, requests Azure's managed certificate without uploading a private key, and checks the public HTTPS health endpoint with certificate verification enabled. DNS changes and issuance can extend the maintenance window. Keep the app running, ingress publicly reachable for validation, and DNS/CAA records correct for automatic renewal.

Keep the original VM, disk and protected settings intact and stopped until acceptance checks pass.

Before any writes are accepted on the managed app, rollback is to deactivate **all** destination revisions and restart the original VM app, then restore DNS. After destination writes begin, restarting the old VM would lose those changes: freeze the destination and reconcile/export its database and files before switching back.

After acceptance, remove migration peering and the source-subnet/DNS access by clearing the migration parameters and explicitly removing both peering resources and the migration DNS link. ARM incremental deployments do not delete resources removed by a false condition. Do not delete the source resource group until backups and rollback-retention requirements are satisfied.

### Scaling and subsequent managed-app updates

Container Apps is intentionally fixed at **one always-on replica**. The current app runs schedulers, file watchers, background work and Socket.IO in-process. Moving hosting platforms does not make those operations horizontally safe.

Before increasing replicas, implement distributed job ownership/leases, durable shared work queues, deduplicated scanners, a shared Socket.IO adapter/session strategy, and a single-run migration process. Revalidate filesystem semantics, concurrency, large uploads and streaming under load. You can independently scale database/storage and vertically resize compute in the meantime.

Even single-revision mode can briefly overlap old and new processes during normal rolling deployments. Before applying an app update, take backups and enter maintenance. Temporarily select multiple-revision mode for manual activation control, list active revisions, and deactivate **every** one:

```bash
az containerapp revision set-mode --subscription "$AZURE_SUBSCRIPTION_ID" \
  -g bookorbit-apps-prod -n bookorbit --mode multiple
az containerapp revision list --subscription "$AZURE_SUBSCRIPTION_ID" \
  -g bookorbit-apps-prod -n bookorbit --query '[?properties.active].name' -o tsv
az containerapp revision deactivate --subscription "$AZURE_SUBSCRIPTION_ID" \
  -g bookorbit-apps-prod -n bookorbit --revision YOUR_ACTIVE_REVISION
```

Wait for deactivation to finish and verify the old replicas have stopped before applying the update with the wrapper and `--confirm-cutover`. The wrapper refuses to deploy while any active revision remains; its template restores single-revision mode. It preserves live hostname/certificate bindings on both plans and updates unless you explicitly supply `customDomains` in your parameters file. Do not bypass the wrapper or clear those bindings accidentally. See [Azure revision management](https://learn.microsoft.com/en-us/azure/container-apps/revisions-manage).

## Validation and operational boundaries

```bash
bash scripts/azure/test.sh
```

This compiles all Bicep targets, checks Bash syntax, renders the real merged Compose configuration, and exercises configuration secrecy, SSH restrictions, backup failures, stopped-source exports and revision-overlap guards with local fakes. The Azure Infrastructure workflow runs it without Azure credentials.

These are local/static checks, not a live Azure deployment or restore drill. Run `plan`, inspect the selected subscription and costs, and rehearse deployment/recovery in your own subscription before production use. Provisioning is incremental, not a destroy/recreate operation. Review changes carefully, particularly disk size, CIDRs, region, PostgreSQL version and resource names.
